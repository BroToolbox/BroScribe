# Security policy

## Status

The first binary release is in preparation. Report issues against the latest source revision and include the commit you tested.

## Reporting a vulnerability

Use [GitHub private vulnerability reporting](https://github.com/BroToolbox/BroScribe/security/advisories/new). If the repository or form is unavailable, contact a maintainer privately.

When reporting:

- Use a private channel. Do not open a public issue for a vulnerability.
- Reproduce with synthetic or openly licensed audio and invented names.
- Never attach real recordings, transcripts, voice embeddings, calendar data, tokens, cookies, keychain or credential-store exports, or personal paths. Redact logs before sending them; BroScribe's logs are designed to contain counts and identifiers, not content, but check them anyway.
- Include the commit, OS and architecture, how BroScribe was built and signed (ad-hoc, Apple Development, Developer ID), and the smallest reproduction.

## Scope

In scope: the code in this repository, its build and packaging scripts, and the CI definition in `.github/`.

Out of scope: vulnerabilities in third-party meeting apps, AI provider CLIs, model files, or the operating system itself. Report those to their vendors. Bugs that only reproduce after an attacker already controls the user's account, or with SIP or Gatekeeper disabled, are hardening reports, not vulnerabilities.

## Security model

See [docs/design.md](docs/design.md) for the detailed security model.

- **Local-first.** BroScribe stores the meeting library on the device. The app keeps audio and voice embeddings local during AI processing. Remote AI providers are off by default and require consent per provider. An enabled summary provider may receive transcript text, notes, bookmarks and instructions. An enabled HTTP embedding provider may receive transcript excerpts and search queries. MCP clients can access data through the tools the user enables. Model downloads contact their configured hosts. Update checks contact GitHub Releases by default and can be turned off in Settings.
- **Data at rest.** The library is ordinary Markdown, JSON, audio and SQLite under the user's account; BroScribe does not encrypt it. Protection at rest comes from the operating system account and disk encryption (FileVault, BitLocker, LUKS). Exports and sensitive temporary files are written with mode 0600.
- **Credentials.** OAuth tokens, client secrets and provider API keys live only in the platform `SecretStore`: Keychain (service `org.broscribe.BroScribe`) on macOS, Credential Manager (service `org.broscribe.BroScribe`) on Windows, Secret Service (service `BroScribe`) on Linux. Each data folder other than the default (`BROSCRIBE_DATA_DIR`, `--data-dir`) has its own namespace, `<service>.profile-<hash>`, so profiles never read, replace or delete each other's secrets; the hash reveals no path. Secrets are read from stdin, never argv or config files, and are never logged or exposed to MCP or agents. BroScribe never reads another application's credential store, browser cookies, or agent-CLI logins, and never bypasses MFA, Conditional Access or tenant refusal.
- **Child processes.** Transcripts reach child processes on stdin or in a mode-0600 file, never in argv. Agent-CLI providers and vendor `mcp add` / `mcp remove` commands run with an allow-listed environment, a temporary working folder and a timeout.
- **Local IPC.** The agent listens only on per-user local endpoints: Unix sockets in 0700 directories with 0600 sockets and peer-credential checks (`getpeereid` on macOS, `SO_PEERCRED` on Linux); on Windows a named pipe with a current-user DACL and peer SID check. There is no TCP listener except the short-lived OAuth loopback redirect during sign-in. The wire protocol is versioned; a client and agent of different protocol versions refuse each other instead of guessing.
- **Recording control.** A mutating command whose answer is uncertain is reconciled through `request.status` with the same request ID, never retried blindly or applied by a local fallback. Recording controls identify the exact session they act on.
- **MCP boundaries.** No MCP tool reads a file it is pointed at: words, contacts and import manifests arrive inline. File exports create only a new visible `.md`, `.txt`, `.json` or `.wav` file outside the library and the data folder. MCP imports never move (and so never remove) an original. An HTTP provider's key and consent are bound to its first configured server address. Every tool checks the MCP switch and maintenance mode before reading its arguments, and live and recording tools refuse when the agent serves another library than the connection. Destructive, account and installation operations stay with the user (design §11), held by a deny-list test and refused by the typed dispatcher on the command and its arguments, whatever a tool is called; no MCP-built command carries a field that reads a local file (notes, contacts, words and manifests arrive inline; only an explicit media file or folder to import is a path). `daemon stop` acts only on the selected profile and unloads the login agent only when it serves that profile.
- **Signed updates.** BroScribe checks GitHub Releases for updates by default (Settings turns this off) and installs only after the user confirms. A release is a manifest signed with an Ed25519 release key; on the default feed with no `trusted_keys` override the compiled public key must verify it, and a nonempty `[updates].trusted_keys` list replaces the compiled key (a custom feed always needs its own keys), and every artifact must match its size and SHA-256 before anything is staged. macOS also requires the Developer ID team `3CHB92P2NM`; Windows requires Authenticode only once a signer pin exists, and until then relies on the signed manifest as Linux does. Redirects are followed only from GitHub release-download paths to GitHub's release-asset hosts, over HTTPS. Before staging and before replacing, the updater refuses an installation folder that is, contains or sits inside the library or a profile's data or cache folder, or that is or contains the home folder (an installation in its own folder inside the home, such as `~/.local/lib/broscribe` or `%LOCALAPPDATA%\Programs\BroScribe`, is fine), and it re-checks every staged file against the hashes recorded from the verified download, so nothing changed on disk after the download is installed. FFmpeg tools a user placed beside the Windows executables are kept as the user's own files, not as part of the signed release. A monthly workflow re-signs the latest published release's envelope with new dates only: it first verifies the existing envelope against the compiled release key (a missing one needs an explicit manual run), re-verifies the same packages, and restores the previous envelope if the upload cannot be read back intact, so renewal never changes what is installed. Two independent safeguards keep personal files from being moved or deleted with the app (and a tree is checked against its recorded inventory, byte for byte, whenever any discovered profile has one for it; paths are compared in one normalised spelling, so this holds on Windows too): the updater and the uninstaller only move or remove an installation folder that holds nothing but a BroScribe release's own files, and they also protect the libraries, data and cache of every profile BroScribe can discover (including a Windows login entry's library), not only the one running the update. Update install, rollback and recovery require an absolute native default data folder and an absolute `BROSCRIBE_DATA_DIR` when nonempty, and absolute library paths in every one of `--library`, `BROSCRIBE_LIBRARY` and the selected profile's config `library` (including an overridden one, which the updater also protects), checked before shared path resolution and mode-lease acquisition, even when an override selects another profile. Rollback and recovery protect the same folders as installation, including an environment library shadowed by `--library`. On Unix the updater's state and staging folders are private (0700, records 0600) whatever the umask, and a record not owned by the user or writable by others is refused (owner-only state is tightened; state owned by another account or writable by a group or others is refused, with the `chown`/`chmod` to check; the highest build any profile verified from the same recorded feed, channel and keys bounds what may be installed). The release key's seed never enters the repository; CI receives it only as the `UPDATE_SIGNING_KEY` secret, in a mode-0600 temporary file deleted after signing.
- **Uninstalling.** `broscribe uninstall` and **Settings → Uninstall BroScribe…** show their plan before acting, act only on confirmation (`--yes`), and are not available over MCP. They delete only entries BroScribe itself writes, from one allowlist shared with the Windows helper and tested against the real writers; anything else is kept and listed, and a preview changes nothing. Signing out of an integration refuses a linked integration folder or state file and removes only the cached photos BroScribe wrote, never the whole folder. Removing a library deletes only the files BroScribe writes in it, and inside a meeting folder only when that folder's meeting record identifies a BroScribe meeting, and its recording only when the record names it; recording audio left without its manifest blocks data removal unless the user also discards unsaved recordings, and a linked journal folder is refused as unverifiable; on Linux a retry command is printed only when it can pin the profile, library, home and XDG config, data and cache roots it depends on (runtime cleanup follows the retry shell's runtime folder unless one was set); every uninstall preview and apply requires an absolute native default data folder, absolute paths for each `--data-dir`, and an absolute `BROSCRIBE_DATA_DIR` when nonempty, and with `--remove-data` or `--remove-library` the `--library`, `BROSCRIBE_LIBRARY` and profile config `library` paths used for selection or protection must also be absolute, as must the default library when it is the effective selection; a refusal names the source to correct; everything else is kept and listed. The Windows clean-up helper's matcher is checked against the Rust one by an executable PowerShell test. They never recursively delete a folder that is, contains or sits inside a library the profile knows, its data or cache folder or the home folder, unless the user chose to delete that folder, and they remove the update staging beside the app only when it provably belongs to a discovered profile. They delete each removed profile's own secrets only (provider keys, integration tokens and client secrets, and any update release-key seed kept in that profile's secret store); on Linux, when the desktop session bus cannot be reached the credential step fails and says so (the other steps still run and the app is kept for a rerun from the desktop) instead of leaving credentials behind silently; `--skip-credentials` leaves stored credentials in place on purpose, and a private list of the profiles found is kept until every one is cleaned, so a retry cannot forget a profile whose credentials are still stored. Disk cleanup of a profile BroScribe only discovered needs the marker BroScribe writes into each data folder it uses, and removing a data folder never removes a library inside it (found by its meeting files or index) that the user did not also choose to remove. The update journal and inventory are removed last, so a failed step can be retried with them. They never remove another profile's secrets unless asked, keep the library and data folders unless the user ticks or passes the delete options, refuse while a recording runs or unsaved recordings exist, and never touch macOS privacy grants, which the user removes in System Settings.
- **Updates and uninstall.** An update or `daemon uninstall` never stops or unregisters a login agent that serves another profile: the job is verified under the registration lock first, and the signed updater requires its own durable admission on any agent it stops. The manual macOS updater holds the profile's startup reservation across the swap and rollback, so an old agent cannot start recording mid-swap, and a completed rollback leaves no rejected build running (a rollback that cannot quit the rejected app is reported as failed and keeps the admission).
- **Stopping the agent.** `broscribe daemon stop` and MCP `stop_daemon` stop an agent only when it is idle, and unload the login job (launchd on macOS, the systemd user unit on Linux) only when the job is idle and configured for the selected profile, or its live process is the agent that answered the selected profile and holds the stop admission, checked again just before the unload. A job for another profile stays loaded, and one they cannot identify is left alone with `login_job_unverified`, so stopping one profile never stops an agent recording for another. The check and the unload hold a per-user lock that every login-registration change also takes, so another profile cannot repoint the job in between, and a job launched through a wrapper is never assumed to serve the default profile. The lock and the long-path fallback sockets live in a per-user folder other accounts cannot create first (the system per-user folder on macOS, `/run/user/<uid>` on Linux; `/tmp/broscribe-<uid>` only on Linux systems without logind); the folder must be a real folder owned by the user and not writable by others, and the file is opened without following symlinks and must be a regular file owned by the user (mode 0600). Login-manager calls time out after 10 s; a stop that timed out reports an error, never success, and the next one verifies the job again. When the login agent runs for another profile while an agent answers for the selected one, the stop is refused and nothing is stopped. They report the agent stopped only when the profile's endpoint and instance lock are both gone (`agent_unreachable` otherwise). The Windows Run entry is never removed by a stop; it starts the agent at the next logon.
- **Recovered recordings.** A recording is published only into the library it was recorded for. One written before journals named their library is adopted into the open library or discarded only after the user confirms (`broscribe record resolve-journal … --yes`); discarding removes only that journal, and neither operation exists in MCP.
- **Calendars and directories.** Read-only scopes only. Accounts, tenants, caches and calendar selections are isolated; nothing is read until the user selects calendars explicitly.
- **macOS permissions.** The signed login-item helper owns the microphone, system-audio and calendar grants. System-audio authorization status uses the private TCC framework loaded at run time; when it is unavailable the status is reported as not determined rather than guessed. BroScribe never resets or edits TCC databases; the user manages grants in System Settings.

## Supply chain

- Rust 1.100.0 is pinned in `rust-toolchain.toml`; `.cargo/config.toml` refuses crate versions published less than three days earlier.
- `Cargo.lock` is committed and every change to it must pass `scripts/check-publish-age.py`, which also rejects git dependencies and yanked locked versions.
- Native sherpa-onnx archives are pinned by SHA-256 in `third_party/sherpa-onnx/SHA256SUMS`; the build fails instead of downloading unverified code.
- The Linux test container is pinned by image digest.
- The CI workflow uses no actions. The merge workflow uses only GitHub's `actions/create-github-app-token`, pinned by full commit SHA, to mint a short-lived repository token for the merge GitHub App. The release workflow uses only GitHub's own `actions/upload-artifact` and `actions/download-artifact`, pinned by full commit SHA; only its draft-release job has `contents: write`, signing credentials are read from repository secrets only when present, and the macOS signing keychain is temporary and deleted at the end of the job. See [docs/release.md](docs/release.md#continuous-integration).

## Known limitations

- Only a release dry run has been signed with the Developer ID certificate and notarized; no notarized release has been published yet. Ad-hoc and Apple Development signatures are for local use only, and macOS may drop permission grants when the signature changes.
- Windows and Linux platform code is implemented and compiled in parts, but its runtime security properties (credential stores, IPC peer checks on real desktops, notifications) are not verified on real systems. See [docs/acceptance.md](docs/acceptance.md).
- Microsoft 365 and Google sign-in have not been validated against a real tenant.
